# Under Stockholm: agent guide

Browser first-person game in a stylized Stockholm metro. Vite + TypeScript + three.js + Rapier. See README.md for the pitch, docs/FEATURES.md for the full list and structure, docs/GAMEPLAY.md for controls.

## Rules

- Use Bun for everything (`bun install`, `bun run dev`, `bunx`). Never npm, yarn or pnpm.
- Code, comments and docs in English. In-world text (signs, announcements, HUD status) is always Swedish. Menus, help and settings come in Swedish and English: `src/game/i18n/text.ts` holds the current language (`src/lang.ts` picks it: the player's choice, else Swedish), `en.json` overrides only those keys, and modules that draw the world import `sv.json` directly. The landing page exists in both languages, `index.html` and `en/index.html`, linked with `hreflang`: change them together (`tests/i18n.test.ts` checks they match).
- Never use em-dashes in code, comments, docs or copy. Use a comma, colon or period, and `|` as a title separator.
- Do not commit unless explicitly asked. No `Co-Authored-By` or other trailers.
- **The recorded announcements never go public.** The clips of the Utrop library in `public/audio/` stay local, ignored by git (only `catalog.json`, their lengths and checksums, is committed): SL does not own the voice and declined to approve it (September 2026), and the rights holder is unknown. The game goes live without them, and videos and copy must not use them or claim the real voice: a plain `bun run deploy` builds with `RECORDINGS=0` (`__RECORDINGS__` false: every call is spoken by the browser's voice, the chime and the door warning are synthesized in `audio.ts`, and no clip is built or uploaded, which the deploy checks). The sounds of people in `public/audio/sfx/` are free and go out. Never deploy with `--with-recordings` unless the user says the recordings have been cleared. `--landing` still deploys the landing page alone (`LANDING_ONLY=1`).
- Deploy only with `bun run deploy` (`scripts/deploy.ts`, to https://understockholm.com/), and only when asked: it refuses a dirty or unpushed tree, runs the whole quality gate and uploads only if every gate passed. It uploads the Worker too (`worker/`, `wrangler.jsonc`): the static build plus the hub, a Durable Object that serves the relay's paths on the same origin in production (docs/DRIFT.md). Never run `wrangler deploy` or any other deploy command directly, and never push with `--no-verify` or `SKIP_CHECK`: a hook blocks them (`scripts/hooks/before-bash.ts`). If the user wants to go around the gate, they run the command themselves.

## Architecture notes

- **Coordinates.** Meters, y up, rail top at y = 0. The line runs along +x (index 0, Kungsträdgården, at x = 0, heading west toward +x). Trains keep left, as on SL's metro: track 1 is at z = -`TRACK_Z` and runs toward +x, track 2 at z = +`TRACK_Z` runs back (`trackSide` in `layout.ts`). All dimensions live in `src/game/layout.ts`: change them there, never hardcode numbers in generators.
- **The network.** Three lines in `NETWORK` (`line.ts`, with the red and green lines in `lines/`), flattened into one list of stations and one of routes with global indices, the blue line first. `routes.ts` (no three.js) lays everything out along x: each line along its first route that is not `shifted`, every other route's own stations (a branch) packed elsewhere along x, so x alone still tells every station apart. A route crosses between two identical copies of the junction tunnel at a portal halfway (a jump in `Timetable.pose`, and `World.portalCopy`); every tunnel out of a junction is `JUNCTION_RUN` long so the copies match. Stations with `shared` are an earlier line's (T-Centralen, Gamla stan, Slussen): the second line's tracks run `LANE` further out, with an island platform between each pair. A `stacked` one (T-Centralen's red and green platforms) lies on two levels as the real one does, a level per direction: it is built as the shared station is and track 1's half folded under track 2's as it is built (`Fold` in `gfx/builder.ts`, `foldedPhysics`), with stairs down through the upper island's floor; `Timetable.pose` puts track 1 there `STACK.drop` lower (`TrainState.y`), its trains crossing over at a portal `STACK.portal` out in the tunnel into tubes of their own, and each island's height is in `StationInfo.levels`. `lineTimetables` builds one timetable per route: on the trunk the routes take turns, a shorter route waits out the difference (modulo its headway) in its turnbacks, and a route that ends where its line goes on turns on a siding. Walkways (`walkway.ts`) join a line's station to the same station on a line built elsewhere. Branch stations, their tunnels and Kymlinge are laid out in a dry pass at start (colliders, zones, interactables) and built for real when the player comes near (`World.later`), one step per frame: `stationSteps`, `tubeSteps`, `extrudeRockSteps` and `Section.finishSteps` are generators that yield between the rock, the furnishing and each baked layer, and the plain `buildStation`, `buildTubes`, `extrudeRock` and `finish` run them to the end. Keep builders working in dry mode (`Section.dry`, `withoutSigns`) and put a `yield` between any new expensive stages. A finished group is warmed on the GPU (`World.warm`, a 1x1 render set up in `boot.ts`) before its first real frame. Sections more than `SHOW_REACH` from the player are hidden, and lazily built ones more than `EVICT_REACH` away are taken down, freed and queued to be built again: add lazily built groups with `World.add`, never `group.add`. Anything a lazy build hands to the rest of the game (a closure, an update, a mesh in a list) gets a `release` in `World.later`, and nothing a build makes goes into a module-level cache: those outlive the build and leak on every trip (`bun run mem` catches it).
- **Depth.** Every underground station has its own `rise` (`stationRise`), so its escalators, ticket hall and street sit at their own height: read a station's `hall.y` and its escalators' `rise` and `run` (`escalatorRun`), never a fixed hall height. Where a hall lies along x, read it from the station (`hallX`, or `halls[k].x` for either of two halls), never from `CAVE_HALF_L` and the escalator's run: a long passage can come between them. A station with a hall at each end has two of everything up there (`StationInfo.halls`): gates, street, weather and street sounds follow the one nearest the player (`World.hallNear`), while the life in the hall stays in the main one. A walkway's two ends may lie at different depths: each is built from its own door, and the crossing in the middle keeps the height relative to it.
- **Landing vs game.** `src/main.ts` must stay tiny and must not import three.js or Rapier statically. The game is loaded with `import('./game/boot')` on click, the whole network view (`?natet`, `src/network/`) the same way. Any static import from `main.ts` into `game/` breaks the landing page budget.
- **No asset files, with four exceptions.** Geometry, textures (canvas) and sound effects are generated at runtime. Do not add models, images or audio files to `public/` or `src/`. The first is the recorded announcement library in `public/audio/` (unedited MP3s from the Utrop library of C20 announcements, see its README): station names, connecting phrases, the warning and the door buzzer. Use those clips for announcements, fetched only after sound is on and only for the current route. Do not add other audio there, and use browser speech for phrases the library lacks. The second is `public/audio/sfx/`: a sneeze, a sigh and bottles clinking, cut from public domain and CC0 recordings (sources in its README) and played through `recordings.ts`, each fetched the first time it sounds. Keep it to sounds of people that synthesis cannot make believable, and only from sources that need no credit. The third is the view from the game used as the landing page picture, `public/og.jpg` (T-Centralen with a train at the platform), and the link preview cards made from it, `public/og-sv.jpg` and `public/og-en.jpg` (the sign, a line of pitch and the way in, in each landing page's language), all rendered by `scripts/og-image.ts`: re-render them rather than editing them, and change a card's words there. The fourth is the README's opening clip, `docs/under-stockholm.webp` (an animated WebP, about 8 MB), recorded from the game by `scripts/readme-clip.ts`: re-record it the same way. Map data is not an asset: the footprints and heights of the buildings round the open-air stations (`scripts/osm.ts`, a file per line in `src/game/world/osm/<line>.json`) and the city round every exit (`scripts/osm-streets.ts`, a file per station end in `src/game/world/osm/streets/`, keyed by `osmKey.ts`, and every station's entrances in `tests/data/osm-entrances.json`, which only `tests/hall-sides.test.ts` reads to check the halls against) are fetched from OpenStreetMap (ODbL, credited in the README and on both landing pages' menus), fetched by the game from its own origin when a build near them first wants them (a lazy build waits in the queue meanwhile, `Lazy.ready`) and built like any other geometry (`world/osm.ts`, `world/streetOsm.ts`); fetch them again with the scripts rather than editing the files, and never ask OSM from the client. The network view has two more of the same kind, fetched when it opens: the buildings of the inner city and round every station (`scripts/osm-city.ts`, a file per 4 km tile in `src/network/city/`) and the ground's heights over the whole metro (`scripts/terrain.ts`, `src/network/terrain.json`, from the Copernicus DEM, credited in the README and in the view). The app icons, `robots.txt`, `sitemap.xml`, `llms.txt`, `.well-known/security.txt` and the host's rules (`_headers`, for Cloudflare and `scripts/serve.ts`: the shared security policy in `server/headers.ts`, also attached to Worker relay responses, and the hashed `assets/` cached for good; the CSP permits the page's own origin and a configured `VITE_GHOSTS_URL` relay, with legacy WASM compilation for Safari 15 in game builds; anything else from elsewhere needs an explicit policy change) are generated at build time (`vite.config.ts`, `scripts/icon.ts`).
- **Site address.** Link previews, canonical and `hreflang` links need absolute URLs, so the pages use `%SITE_URL%`, filled in at build time from `SITE_URL` (for example `SITE_URL=https://example.se/ bun run build`). Without it the build warns and points at the local production server.
- **World building.** `World.load` builds the trunk a slice at a time behind the loading screen in `boot.ts` (`nextFrame` in `frames.ts` yields to the browser, also in a hidden tab); `World.create` does the same at once. `World` builds one `Section` per station, tunnel and turnback cavern. A `Section` has `MeshBuilder` layers (`lit`, `floor`, `tactile`, per-texture `artLayer`, `unlit`), a list of bake lights and an `extras` group. `finish()` bakes the lights into vertex colors and returns one mesh per layer, all using shared `MeshBasicMaterial`s. Keep static geometry in these builders so draw calls stay low; only signs, displays and animated things go in `extras` as separate meshes. The baked layers let go of their vertex arrays once they are on the GPU (`dropArray`), so never read or change them after `finish()`; a lost WebGL context reloads the page back to where the player stood.
- **Open air.** Stations with `open` (and not shared) are built above ground: canopy, fences, scenery (`outdoor.ts`), and the way between stations is split into open and tunnel stretches with tunnel mouths (`World.stretches`). Open-air sections pass `outdoor` to `Section`: their materials are scaled by `setDaylight` from the `Sky`, and `World.outdoorAt` blends the fog, the view distance and the rain around the player.
- **Lighting.** Static world lighting is baked (`bakeLighting` in `gfx/builder.ts`), there are no real-time lights except one `HemisphereLight` used by the trains' Lambert exterior. To light something, call `section.light(...)` before `finish()`. Large surfaces need `gridQuad` or `box(..., cell)` subdivision so light pools show up.
- **Paint.** Colors are `RGB` tuples (`gfx/color.ts`). A `Paint` is a flat color or a function of vertex position and normal, evaluated when the triangle is added. Station themes (`line.ts`) are paint functions plus ambient and lamp colors.
- **Physics.** Rapier with no dynamic bodies: static cuboid colliders from `Physics.box` / `tiltedBox`, a kinematic character controller for the player and train colliders that are parentless and moved by hand (attaching them to a kinematic body makes the controller stall). Every walkable surface needs a collider next to its mesh.
- **Timetable.** `Timetable.stateAt(time + offset)` on the service's route timetable (`Service.timetable`) is the single source of truth for train position, speed, doors and phase. It is a pure function: do not add per-train state that the timetable cannot reproduce. The emergency brake is the one local detour (`emergencyBrake.ts`): a temporary override, then a delay that is dropped in a turnback out of sight. Departure boards, announcements and the line map are all derived from it in `boot.ts`.
- **The power cut.** The one shared detour from the timetable: on days picked by the date (`powerCut.ts`) the power goes for a few minutes and `cutClock(time)` runs every timetable clock down to a standstill, holds it and lets it catch up afterwards. Anything that places trains from the timetable reads it through `cutClock` (`boot.ts`, and the landing map and the network view through `landing/trains.ts`). The dark itself is a patch to the shared world materials (`torchify` in `powerLights.ts`): give any new baked world material the same patch.
- **Clock.** Game `time` is Unix epoch seconds (`clock.ts`), so all visitors share trains, Silverpilen and inspectors. `Operations` decides per loop whether a train is in service (night break), so trains only appear and disappear in the east turnback. Anything shared between players must be a pure function of `time`. The driver mode's practice train is the one deliberate exception and runs only while regular service is hidden.
- **Real trains.** On by default wherever there is a relay (off in the pause menu, remembered; `?debug` keeps to the timetable unless it was turned on), `realService.ts` lets SL's live metro drive the game's trains, line by line (`RealTrains.live(line)`): a line follows SL once SL reports trains from a quarter of its stations, so without GTFS only the blue line does (the Transport API's quota covers its stations alone) and the others keep to the timetable. Each line has spare trains for real journeys (`REAL_SLOTS` in `boot.ts`, built with the rest), and a service's `slot` is its place among its line's trains. Expected departures per station come from the relay's shared copy (`server/feeds.ts`, read by `sl.ts`) so SL's load does not grow with visitors: built from Trafiklab's GTFS Regional feeds when the relay has `TRAFIKLAB_RT_KEY` and `TRAFIKLAB_STATIC_KEY` (`server/gtfs.ts`), else from SL's keyless Transport API, in the Transport API's shape either way; the relay is the page's own origin (the Bun relay behind the dev server, the hub in production; `VITE_GHOSTS_URL` overrides it, `off` turns it off, and then the mode and the landing map's toggle are hidden). Never poll SL, SMHI, Open-Meteo or Sveriges Radio from the client: every live feed goes through the relay. Each real journey becomes a warped timetable clock (`Service.clock` and `rate`), so doors, announcements, commuters and fares keep working from `timetable.stateAt(clock)`. Always read a train's state through `stateOf(svc)` in `boot.ts`, never `time + offset`. Trains hold at platforms until SL's departure and run slower in the tunnels; a leg is fixed once a train leaves a station. Each journey runs on its line's route timetable, from turnback to turnback. Stale data falls back to the timetable. The first minute's seat on an arriving train waits a few seconds for SL's trains. Silverpilen keeps running while SL drives the blue line (`silverReal.ts`): her hourly run waits in the east turnback for a gap as wide as the timetable's, then runs on a clock of her own that slows behind a real train ahead (she stands in the tunnel as at a red signal), and she fades where she is if a real train catches up from behind or she is held for minutes. That is local state, so shared rides (on her or any train) are off in this mode.
- **Riding.** The player rides by being carried by the train's per-frame `delta` (and the escalator's belt velocity), not by parenting. `boot.ts` decides who is riding before trains move each frame.
- **Main loop.** `boot.ts` owns the frame: trains, physics step, player, hazards (falling, being hit), HUD, audio and a once-per-second update of departures, clocks and the map. Keep new per-frame work cheap. The render resolution adapts (`resolution.ts`): 30 frames whose median is slower than 22 ms (about 45 fps) lower the pixel ratio a notch, so frames wandering either side of the line still count and a lone hitch does not; ten quick seconds raise it again. Frames held up by the game's own code do not count, and a notch that did not make frames quicker (a browser capped at 30 fps) is given back.
- **Adding a station** is data only: an entry in a line's `stations` with a `Theme`, its place on the network map (`map`), its weekday boardings (`riders`, which set how crowded it is and how long trains stand there), its SL site id (`sl`, for real trains), and on a branch its `branch` (route number, or numbers) and optional `gap` from the previous station; `open` if it lies above ground, `rise` for how far its escalators climb to the ticket hall (its real depth less the hall's 8.5 m under the street, at least 7 so the hall clears the tunnels), `halls` for its ticket halls as its real plan has them (`end` for which end of the platform, `corridor` for a long walk from the escalators, `incline` for an inclined lift, `from` for escalators that start out on the platform and climb through the ceiling (tiled or the rock's crown, or in the open past the roof), and in the open `down` for a hall under the tracks with stairs up beside them (with `from` negative the flight runs down past the platform's end to a hall under the open track beyond it, as at most suburban stations); a hall at the staff door's end moves the door beside its escalators, `SIDE_DOOR`; `World` throws on halls that do not fit, such as one toward open air too close, and `tests/halls.test.ts` checks the data), `look` for a tiled station's ceiling, floor and columns (`columns: 'none'` in a rock cave leaves out its piers), a `theme` and at most one painted vault (`gfx/art/<line>.ts`) after the real station's colours and art, its own objects on the platform in `world/details/<line>.ts`, and in the open its roof in `lines/canopies.ts`. The world, tunnels, timetable, signage and boards adapt automatically. The landing page's live line map keeps its own copy of every line's names, branches, gaps, routes, SL site ids, boardings and map places in `src/landing/lines.ts` (so it stays free of three.js); add the station there too, and `tests/line-map.test.ts` checks the two agree. The map builds the game's own timetables and services from it (`serviceSlots` in `routes.ts`), so it shows the trains you meet.
- **Debug.** `__us.step(seconds, rate)` runs frames by hand, also in a hidden tab (useful for headless checks). `?debug` never pauses (a click on the canvas still takes the mouse for looking) and exposes `window.__us`: `physics`, `player`, `world`, `timetable`, `services`, `renderer`, a writable `time`, `goto(i)` and `info()` (draw calls, memory, feet position, riding, location). Optional URL params `x`, `y`, `z`, `yaw`, `pitch` set the camera pose; `t` (seconds from a fixed weekday noon), `clock=HH:MM`, `weather=...`, `silverpilen` and `disruption=...` set time, weather, the ghost train and a made-up SL traffic message, for headless screenshots. `showcase` starts the tour, `liv` a life on the blue line (`__us.lifeScene(i)` stages one of its stations), `stromavbrott` a power cut a few seconds in, and `stage` seats you on an arriving train on the first resume, as outside debug. The network view exposes `window.__net` (`step`, `dive`) under `?debug`. For looks, `bun run shots` (with `bun run dev` running; a line or station names to take fewer) photographs every station's platform in a held moment into `shots/` (ignored by git) with a contact sheet per line, the stations changed since the run before framed in red: run it after changing stations, themes, roofs or `station.ts`, and look at the sheets. `bun run tour` does the same for the rest of each station, the platform, every ticket hall and the street out of it (`scripts/tour.ts`, a sheet per station in `shots/tour/`): run it after changing halls, streets or the city round the exits. `__us.street(station, k)` stands on the street out of hall `k`, or on the square beside the tracks from a hall under them. `tests/station-looks.test.ts` checks that no station falls back to the shared look. For memory, `bun run mem` fails if travelling the network, a life on the blue line or the driver's cab leaves anything behind (`scripts/mem.ts`). For speed, `bun run fps` measures real frame rates in headless Chrome on this machine's GPU, as a desktop and as a phone (`scripts/fps.ts`, with `--why`); `__us.ride()` seats you on the next train, `__us.resetResolution()` puts the adaptive resolution back to full (`fps` does it before timing each scene), `__us.slowFrames()` lists the slowest recent frames by part, `__us.perf()` times frames (logic and render apart), `__us.laps()` splits a frame into its parts, `__us.hotspots()` lists the heaviest methods and `?spector` with `__us.spector()` captures a frame in SpectorJS, the last two in the dev server only; the `three-webgl-game` skill in `.claude/skills/` has the workflow. Debug time does not follow the wall clock.
- **Captions.** Life around the player (platform and hall life, the carriage, critters, festivities, the regulars, ambience) talks through `ambient` in `boot.ts`, not `hud.say`: lines that only say what can be seen, and people's chatter, are never shown, the rest at most one every 20 s and voices one every 25 s. Put new ambient lines there; the discovery book still sees every line. Captions for announcements and for what the player does go straight to `hud.say`.
- **The relay.** Two implementations with one set of answers: the Bun relay (`server/ghosts.ts`, `server/feeds.ts`, `server/perf.ts`, `server/errors.ts`) in development and in `bun run serve:prod`, and the hub (`worker/hub.ts`, one Durable Object behind `worker/index.ts`) in production. What they share lives in `server/pose.ts` (other players: protocol, limits, snapshots), `server/feedCore.ts` (the feed cache and SL's budget), `server/gtfsFeed.ts` and `server/gtfs.ts` (GTFS Regional, the zip read as it downloads: a Durable Object has 128 MB), `server/perfCore.ts` and `server/errorCore.ts`; change behaviour there, never in one relay alone. The shared code must run on Cloudflare's runtime: no Bun APIs and nothing that imports three.js (use `src/landing/lines.ts`, not `game/line.ts`). The rate limits are listed in docs/DRIFT.md, section 3, and `scripts/worker-check.ts` (in the quick gates) checks them end to end in `wrangler dev`: add a check there with any new limit. `bunx wrangler dev --port 8911` runs the Worker locally on the last build.
- **Zones and use.** Named areas (`world/zones.ts`) override `World.locate` for staff rooms and Kymlinge. Things the player can use register an `Interactable` in `world.interactables`; `E` and the touch Use button act on the nearest one.


## Quality gates

`bun run check` is the gate (`scripts/check.ts`), and nothing is done until it has passed. It comes in levels, cheap to dear, and starts the servers itself:

```bash
bun run check --quick    # types, tests, the build with its size budgets, the Worker's limits: seconds
bun run check --smoke    # the quick gates, one leak scenario, the two heaviest scenes as a phone: 1.5 minutes, any game change
bun run check --perf     # the quick gates, every leak scenario and scene, the time to playing: 9 minutes, changes to the world, the build steps or the frame loop
bun run check --web      # the quick gates, Lighthouse and pa11y on both landing pages: 3 minutes, landing page changes
bun run release          # all of it, 12 minutes: what `bun run deploy` runs before it uploads
```

Keep routine feedback fast: use typechecking and the relevant test files while editing, then the appropriate local gate above. GitHub's `Leaks (manual)` workflow is an optional background diagnostic, not part of the push or deploy gate. Its first full Linux CPU run took 43 minutes. Do not launch it or wait for it on routine edits or pushes: use the local GPU memory/performance checks for resource changes, and the Linux workflow when explicitly requested or investigating Linux-specific behaviour. Keep it manual even after a passing run. The full release gate still runs before every deploy.

It fails on anything under the floors in `scripts/check.ts` (frame rate, the share of frames over 20 ms, frames over 50 ms, where the adaptive resolution landed, seconds to playing, Lighthouse 100 on Performance, Accessibility and SEO, zero pa11y errors) and on anything worse than `perf/baseline.json` by more than the noise between runs (fps, frames over 20 ms, draw calls, triangles, loading, bytes). A scene that misses is timed once more and fails only if it misses again, so a lone hitch from something else on the machine does not fail the gate, and a machine already busy before the timing is noted in the output: close heavy apps before measuring. A change that is meant to cost (a new station, a heavier scene) is accepted with `bun run check --perf --accept`, and the new baseline is committed with it. Every run writes `perf/last-run.json`.

It runs on its own too, at the level each moment can afford. `git push` runs the quick gates, and `--smoke` when the game changed (`scripts/hooks/pre-push`, installed by `bun install`), so a push never waits more than a minute or two, and not at all when the last check already passed at that level on exactly the tree being pushed: every run records the tree it checked (`scripts/tree.ts`, git's tree hash of every file not ignored, the baseline left out), and `scripts/tested.ts` compares it with each pushed commit's. The whole gate runs before every deploy, inside `bun run deploy`, so nothing goes live unmeasured. GitHub Actions runs the same gates again on a clean checkout (`.github/workflows/`, free while the repository is public): the quick gates on every push to main and every pull request, `--web` when the landing page changed, and every leak scenario by hand. The runners have no GPU, so Chrome draws WebGL on the CPU there (`scripts/chrome.ts`, `SOFTWARE_GL=1` does the same on the Mac), and frame rates and the time to playing stay local. It can also run every night on what was pushed (`bun run nightly --install`, a LaunchAgent on the developer's Mac, with the results in `perf/history.jsonl` and `bun run nightly --trend`), but that is switched off for now: do not install it unless asked. In Claude Code, deploy commands other than `bun run deploy` and pushes that skip the gate are blocked, every edit to a TypeScript file is typechecked and tested at once, and a session that changed the landing page cannot end before a passing `--web` (`.claude/settings.json`, `scripts/hooks/`); a change to the game is gated by the push. Say what the numbers were in the answer.

When something fails, run the piece on its own to find the cause: `bun run mem` (the `three-webgl-game` skill says how to find a leak), `bun run fps --why` (what the slow frames spent their time on), `bun run load`, and the game in a browser with `?debug`. With an Android phone over USB, `bun run check --perf --device` (or `bun run fps --device`) measures on its real GPU as well; the emulated phone in the ordinary run only slows the CPU. After launch, the relay's `/perf` page shows how it runs for players (`server/perf.ts`, `src/game/telemetry.ts`: one anonymous report per visit), and `/errors` what went wrong in their games (`server/errors.ts`, `src/game/crash.ts`: at most three reports per visit). A frame that throws stops the loop and shows a card that reloads the page back where the player stood.
